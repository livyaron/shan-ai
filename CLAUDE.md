## 4. Critical Operational Guardrails
- **Deployment is Railway-ONLY.** The local Docker stack is retired. All DB commands run against the Railway DB: `psql "$RAILWAY_DATABASE_URL" -c "..."` (URL in local `.env`, never commit it — repo is public). Never start a local Docker instance while Railway is live — it steals Telegram polling AND double-sends the 07:00 missions digest and overdue alerts.
- **The "BIGINT" Fix:** After a fresh DB, MUST run:
  `psql "$RAILWAY_DATABASE_URL" -c "ALTER TABLE users ALTER COLUMN telegram_id TYPE BIGINT;"`
- **is_relevant columns:** After a Railway deploy with new schema / fresh DB:
  `psql "$RAILWAY_DATABASE_URL" -c "ALTER TABLE decisions ADD COLUMN IF NOT EXISTS is_relevant BOOLEAN NOT NULL DEFAULT TRUE, ADD COLUMN IF NOT EXISTS irrelevant_reason TEXT, ADD COLUMN IF NOT EXISTS irrelevant_at TIMESTAMP, ADD COLUMN IF NOT EXISTS irrelevant_by_id INTEGER REFERENCES users(id);"`
- **roleenum VIEWER:** DB enum may lack values added in code (`app/models.py` RoleEnum). After fresh DB, run:
  `psql "$RAILWAY_DATABASE_URL" -c "ALTER TYPE roleenum ADD VALUE IF NOT EXISTS 'VIEWER';"`
- **judged_against_gold:** After fresh DB / deploy with new schema:
  `psql "$RAILWAY_DATABASE_URL" -c "ALTER TABLE query_logs ADD COLUMN IF NOT EXISTS judged_against_gold BOOLEAN;"`
- **eval_runs.failed_questions:** After fresh DB / deploy with new schema:
  `ALTER TABLE eval_runs ADD COLUMN IF NOT EXISTS failed_questions JSON;` (Railway DB)
- **eval_gold_answers live cols:** After fresh DB / deploy with new schema:
  `ALTER TABLE eval_gold_answers ADD COLUMN IF NOT EXISTS last_live_verdict VARCHAR(10), ADD COLUMN IF NOT EXISTS last_live_score DOUBLE PRECISION, ADD COLUMN IF NOT EXISTS last_live_at TIMESTAMP;` (Railway DB)
- **missions table (חדר מבצעים):** auto-creates at startup via `Base.metadata.create_all` — no manual SQL needed on fresh deploys. **Future** columns need `ALTER TABLE missions ADD COLUMN IF NOT EXISTS ...` on the Railway DB. `status` is intentionally VARCHAR — never convert to a PG enum. User deletion reassigns the deleted user's missions to the deleting admin. Mission status is **open/closed only** — `in_progress` is **removed** from `MissionStatusEnum` (legacy rows are normalized to `open` at startup); progress is reported via status updates, not a status change. `ACTIVE_STATUSES` in `missions_menu_service.py` is the single source of truth for "is this mission live?" — never inline the status values (the web template gets it via the `active_statuses` context key).
- **משימה חדשה (24 שעות):** `NEW_MISSION_HOURS` + `is_new()` in `missions_menu_service.py` are the ONLY definition of "this mission was just opened" — the four web layouts, the wall display, the Telegram card and the XLSX (`חדשה?` column) all call it, so the window is changed in exactly one place. `created_at` is naive UTC; `is_new` compares in UTC and `format_created_il` is what renders it to Israel-local `DD/MM/YYYY HH:MM` on screen. On the wall the flag is a badge + ring and NEVER a tone: colour there means time-to-target only. A mission inside the window is also exempt from `is_silent` — nobody owes a status report on something opened this morning. Changing `OPEN_HEADERS`/`CLOSED_HEADERS` means bumping `KIND_REPORT` (`report_v4`), or the day-cache keeps serving yesterday's layout.
- **סגירת משימה (מתי ומה נכתב):** `set_status` stamps `completed_at` for **both** `done` and `cancelled` — a cancelled mission also left the board at a moment, and the NULL is what left every cancelled row in the XLSX with no closing date. Nothing that counts "done" reads the field alone: every such query filters `status == DONE` first. Historical cancelled rows are still NULL, so `missions_report_service._closed_at()` falls back to the closing note's timestamp and then `updated_at` — the closed sheet's `נסגרה בתאריך` column and its sort order both read THAT, never `completed_at` raw (which keeps its own untouched `הושלמה בתאריך` column). `_close_update()` is the note written while closing (`kind == 'close'`); `_update_text` marks it 🔒 so a plain progress report is never mistaken for the reason a mission closed.
- **mission_updates table (עדכוני סטטוס):** auto-creates at startup via `Base.metadata.create_all` — no manual SQL needed. **Future** columns need `ALTER TABLE mission_updates ADD COLUMN IF NOT EXISTS ...` on the Railway DB. `author_id` is nullable and `author_name` is a snapshot, so deleting a user never erases who reported what. `kind` is `NULL` for an ordinary update and `'close'` for the note written while closing a mission; it is ALTERed in at startup (`app/main.py`), since `create_all` never alters an existing table.
- **users.war_room_style (תצוגת חדר מבצעים):** per-user board layout, ALTERed in at startup (`app/main.py`) since `create_all` never alters an existing table. NULL = the default style, so an existing user keeps the screen they know. `app/services/war_room_styles.py` is the single source of truth for which styles exist — the router, the templates and the tests all read the list from there; never re-spell a style key inline. Every layout renders the SAME router context and posts to the SAME endpoints; a new layout is one template plus one row in `STYLES`. `?style=<key>` overrides the saved preference for one request (that is how the wall display runs without a user of its own). `&tv=1` additionally drops the navbar and the style switcher — that is the URL a wall-mounted screen loads.
- **לוח מצב (wall display):** `app/services/war_room_wall.py` owns the card tones, the worst-first order and the page size; the template only draws what it returns. The screen rotates through EVERY active mission (undated included) and reloads itself only at the end of a full cycle — never re-spell a tone key or the page size in a template or a router.
- **משפט השעה (wall quotes):** `app/services/war_room_quotes.py` is the ONLY place quotes live — ~200 curated lines on two shelves (`stoic` / `wry`). **Never let a model generate a quote**: a fabricated attribution at 40pt in front of 500 engineers is a lie with a font size. The LLM writes only the one connecting sentence. Attribution is author-only (no chapter and verse), Hebrew sources are quoted not translated, disputed attributions are excluded rather than softened, and no straight `"` anywhere (JSON safety) — tests enforce all four. `pick_quote` walks each shelf in a shuffled, cycle-aligned order so every quote shows exactly once before any repeats (~8 days per shelf). To add quotes, append rows to `QUOTES` — nothing else needs to change. The QUOTE holds for the full hour (a wall that swaps its quote mid-hour reads as broken); only the sentence under it alternates, every `SWAP_MINUTES` (5), between the AI line and the computed one — the hour opens on the computed line because the AI line for a new hour does not exist yet. Every `_FALLBACKS` shelf must hold an ODD number of lines: the computed line takes every other band, so it strides its shelf by two, and an even shelf shows three sentences twice each per hour. A test enforces it.
- **כרטיסי KPI כפילטר:** `app/services/war_room_kpis.py` is the single source of truth for which KPI cards exist, which stat each one reads and which rows `?kpi=<key>` selects — the router, the cyber board and the table all read it from there; never re-spell a key or a where-clause in a template. A KPI **owns the status** while it is on (the status `<select>` is disabled), otherwise `הושלמו השבוע` filters itself against `status=active` and answers with an empty board. The counters stay board-wide on purpose: a KPI row that shrank to match its own filter stops being a summary. Only the two board layouts (`cyber`, `table`) carry it — פוקוס is personal and לוח מצב is a screen nobody clicks; a test enforces that.
- **משימת המשך (parent_id):** `missions.parent_id` links a follow-up to the mission it grew out of, ALTERed in at startup (`app/main.py`) since `create_all` never alters an existing table. **SET NULL, never CASCADE** — losing a parent must not delete open work. `app/services/war_room_chain.py` is the only place the chain is walked (`load_chains`, cycle-guarded, `MAX_DEPTH`); the layouts draw what it returns. A closed parent is hidden from the open board by the existing status rule alone — nothing extra hides it, so don't add anything. Creating a child goes through the ordinary `/create` endpoint with a `parent_id` field: a child mission is a mission in every other way.
- **היסטוריית דחיית יעד (mission_due_changes):** auto-creates at startup via `Base.metadata.create_all`; **future** columns need `ALTER TABLE mission_due_changes ADD COLUMN IF NOT EXISTS ...` on the Railway DB. `oms.needs_due_reason(m, new_date)` is the ONE definition of "this is a postponement" (an existing target moved) — the web endpoint, the batch bar and the Telegram bot all ask it before demanding a reason, and `oms.update_mission` asks it again before writing the history row, so no path can move a date silently. Setting a FIRST date is not a postponement and stays one click. `requested_by` is a snapshot string (and often not a user at all — a committee, a contractor), `requested_by_id` is set only when a system user was picked. The card's counter is `len(rows)` via `oms.postpone_label`, which is why a re-save of the same date must never write a row.
- **mission_report_cache table:** day-cache for the חדר מבצעים XLSX + AI summary, auto-created via `Base.metadata.create_all`. The in-process dicts in `missions_report_service` die with the container, so this is what keeps the 🧠 סיכום AI button instant across a Railway redeploy. Warmed at 04:10 daily, restored into memory at startup, and repaired by an hourly watchdog when today's summary is missing. Never treat it as a source of truth — every read and write is best-effort and swallows its own errors.
- **קובץ המאסטר השבועי — היסטוריה (PLAN.md P0):** `project_weekly_entries` auto-creates via `create_all` (one row per project per `פירוט שבועי <date>` column; **future** columns need `ALTER TABLE project_weekly_entries ADD COLUMN IF NOT EXISTS ...`). The five captured columns (`finish_date_text`, `controller`, `short_supervisors`, `short_testers`, `critical_tier`) on `projects` + `project_snapshots` are ALTERed in at startup (`app/main.py`). Snapshots are stamped with the **report date** (`project_sync.resolve_report_date`: filename → newest weekly column → today), never the upload day. A file older than `_report_horizon` is **replayed as history**: it adds snapshots + weekly entries, never touches live `projects` rows, returns no `identifiers` (the caller deactivates every project missing from that list — an old file would otherwise kill newer projects), and fires no briefs/reports. Weekly entries keep the newest `source_report_date` — an older file never overwrites a newer file's text. `דוח שבועי טיוטה` sheets are skipped entirely. `יעד חשמול מסתמן` prose stays prose in `finish_date_text` — never extract a date out of it. Historical files go in through the admin-only `POST /dashboard/projects/backfill` ("📚 טעינת היסטוריה" on the projects page): `force_history=True` for every file, oldest first. `pick_master_sheet` picks the `…עדכני` sheet when no sheet is given — never go back to "first sheet" (newer workbooks open with a one-cell macro sheet).
- **מנוע דפוסים (PLAN.md P2):** `app/services/pattern_service.py` — **no LLM computes a number**; every metric is `{value, n, confidence, caveat}` and the thresholds live as named constants at the top of the module, nowhere else. `load_frames` is its only DB access; `compute_patterns` is pure and tested on synthetic frames. `app/services/stage_sectors.py` is the ONLY stage → sector map — never re-spell a stage or sector key; `עבודה אזרחית והרכבות` belongs to two sectors, so sector totals are never summed into a division total. Report-date clustering is measured from a cluster's first date, never chained. Page `GET /dashboard/projects/insights` ("🧠 דפוסים וסיכונים"); raw JSON `GET /dashboard/projects/patterns` stays admin-only.
- **מי רואה מה בדפוסים (PLAN.md P3):** `app/services/insight_access.py` is the ONLY place that decides it — `scope_for` reads the role (admin / `users.sector` / confirmed `manager_aliases`), `view_for` is pure and filters the engine output; the template only draws `view`. Admin: everything. `pm_dept`: all projects + league. Sector manager: projects whose current stage is in the sector + that sector's row and attribution. PM: own projects + the named league (D3). Leading indicators, risk topics, update waves, data health and the lists are admin-only (PLAN.md §8.3–8.4). `users.sector` is ALTERed at startup; `manager_aliases` auto-creates. Links are set only by an admin at `/dashboard/projects/insights/access` — **never auto-link a name**: a wrong link shows a PM someone else's projects. `stage_sectors.ASSIGNABLE_SECTORS` (no `unknown`) is what a user can be given. **View as:** an admin previews any viewer with `?as_user=<id>` / `?as_sector=<key>` / `?as_manager=<name in the file>` (`insight_access.preview_scope`) — the preview never carries admin power, and the params are ignored for non-admins (tested). **Drill-down:** every number on the page links to `?drill=<kind>&dv=<value>&dm=<metric>`; `insight_access.drill_for` returns the rows behind it and only ever filters what `view` already allows — a drill can never widen access (tested: each drill's row count equals its number). Slip/baseline moves are kept as `events` in the engine output for this.
- **טקסונומיית נושאים (v2) ודיווח "זהה":** `RISK_CATEGORIES` anchors ambiguous stems on Hebrew word edges (`_B`/`_E`) — v1's raw substrings read "הרכבת" (assembly) as a train (~230 false "outside party" hits, which manufactured the only leading-indicator signal), "מוקדם" as a control centre, "הגורמים"/"כרמיאל" as רמ"י, "לעלות"/"בעלות" as cost. **Before adding a stem, list what it actually matches in the weekly texts** (a test holds the known traps). A weekly report counts as a repeat by `near_same` (≥95 similarity, punctuation ignored), never by exact hash — a one-letter typo fix is not a new report. Weeks in stage carry `weeks_lower_bound` when history starts in that stage; show them as "לפחות". `קרקע` alone is NOT land ("עלייה לקרקע" = contractor on site, "תת קרקעי" = cable, "זיהום/יועץ קרקע" = soil) — only land-rights phrases count. **Move events** are measured against the last DATED report (`undated_between`), so a target written as text for a few weeks never swallows the move across the gap; a wave still counts consecutive pairs only, and its drill filters on both `from` and `to`. `חסם לטיפול <who>` in the file's לטיפול column is a flag (סמנכ"ל = high). **Drift** (`forecast_moved_months`, `forecast_drift`) runs from each project's OWN first dated report to its last (`_own_drift`, needs ≥2 dated reports) — never from the division's first report, which read as "never moved" for any project whose first report had no date. `ציוד/אספקה` counts supply only — the equipment nouns (שנאי/ציוד/מפסק) matched 1,599 of 1,898 entries; bare `נתי` is a person. A target cell starting `חושמל` is energized, not undated (`ENERGIZED`).
- **דף פרויקט:** `GET /dashboard/projects/p/<identifier>` — `pattern_service.project_history` (pure) builds status, report timeline, weekly reports (newest first, repeats marked), move events, topic evidence quotes and the risk read-out. Every risk line is a rule over that data (no LLM). Visible only if the project is in the viewer's `view` (admin / pm_dept: every project, including inactive). Two interactive charts, data from `project_chart.delay_story` / `risk_matrix` / `risk_column_changes` (pure), drawn by `templates/_project_charts.js` (inlined): **delay over time** in months on ONE axis (cumulative forecast slip, baseline slip, gap vs plan — never dates and months on the same chart), crosshair snapping to the nearest report with one tooltip for all series plus stage, moves, targets, topics, risk-column change and the week's report; **risks over time** as a topic × week matrix with the exact quote on hover. Data goes into the DOM with `textContent` only (a test checks `innerHTML` never appears). Colours: reference palette dark slots 1–3 (#3987e5 / #d95926 / #199e70), validated against #0f1826 with `validate_palette.js`. Every chart has a table twin.
- **No Data Loss:** NEVER run destructive SQL (DROP/TRUNCATE/DELETE without WHERE) or delete the Railway Postgres volume without explicit confirmation.
- **הבוט על Railway עובד ב-WEBHOOK, לא polling** (`app/main.py` startup: `RAILWAY_PUBLIC_DOMAIN` קיים ⇒ `set_webhook`; polling הוא רק מסלול הפיתוח המקומי). ה-registration הוא **גלובלי לטוקן**, לא לקונטיינר — ולכן:
    1. **אסור ל-`deleteWebhook` ב-shutdown.** בדיפלוי הקונטיינר החדש רושם webhook בזמן שהישן נכבה; `deleteWebhook` בדרך החוצה מוחק את הרישום שהחדש בדיוק יצר, האתר נשאר חי, הדיפלוי ירוק — והבוט אילם עד ריסטרט ידני. זה הבאג שאובחן ב-2026-09-21.
    2. **כל instance מקומי שמריץ polling מוחק את ה-webhook של הפרודקשן** — PTB קורא `delete_webhook` בתוך `start_polling` תמיד (`telegram/ext/_updater.py`), לא רק "גונב" את ה-polling.
    3. `_webhook_watchdog` ב-`app/main.py` (כל `WEBHOOK_WATCHDOG_SECONDS`=300) שואל את טלגרם אם הרישום עוד מצביע עלינו ומתקן אותו; תיקון רץ עם `drop_pending_updates=False` (הודעות שנצברו בפער הן שאלות אמיתיות), האתחול רץ עם `True`.
    4. **אבחון מבחוץ:** `GET /telegram/webhook_status` (מה טלגרם חושב: `healthy`, `registered_url`, `pending_update_count`, `last_error_message`) ו-`GET /telegram/webhook_repair` (רישום מחדש מיד, ללא המתנה ל-watchdog). זו התשובה היחידה לשאלה "למה הבוט לא עונה" כשהאתר עצמו עובד — `/health` לא יודע כלום על טלגרם.
- **Public URL:** `https://shan-ai.up.railway.app`. Never hardcode it in `app/` — use `settings.public_base_url`, which prefers Railway's auto-injected `RAILWAY_PUBLIC_DOMAIN` so a domain change self-heals. A test enforces this.
- **Build Cycle:** Pushing to `master` deploys itself. `.github/workflows/docker-build.yml` builds the image and runs the no-DB tests; a green run on `master` fires `.github/workflows/deploy.yml`, which does `railway up --detach --service easygoing-endurance` and then polls `/health` until it reports the new commit — so a **green deploy job is proof the commit is serving**, not merely uploaded. `./deploy.sh` from a machine with the Railway CLI is the manual fallback, not the primary path. **Verify every deploy landed**: `curl -s https://shan-ai.up.railway.app/health` reports the deployed `commit`; compare it against `git rev-parse --short=12 HEAD`. A 404 on a route you just added means the build is behind, not that the route is missing.
- **Always deploy after building (standing instruction, 2026-08-23):** don't stop at merging to `master` — verify the deploy landed, every time, without asking.
- **Remote sessions CAN deploy (corrected 2026-09-04).** The old note here said they could not, and it was wrong — it cost a "deploy still owed" report on a deploy that had already fired and failed unnoticed. What is true: the sandbox itself still cannot reach Railway (`shan-ai.up.railway.app`, `railway.app`, `backboard.railway.*` are all denied at the egress proxy) and holds no Railway CLI or `RAILWAY_TOKEN` — so **never `curl /health` from the sandbox to check a deploy; it will always look down.** But the deploy runs on a GitHub Actions runner, which is not in the sandbox, and the GitHub MCP tools drive it: `actions_list` (`list_workflow_runs`, branch `master`) to find the run, `get_job_logs` with `failed_only` to read a failure, `actions_run_trigger` (`rerun_failed_jobs`, or `run_workflow` on `deploy.yml`) to retry. Read the deploy job's own `/health` polling log for the verification, since the sandbox cannot do it.
- **A `railway up` timeout is not a code failure.** `error sending request ... backboard.railway.com ... Operation timed out (os error 110)` during Uploading is Railway's API being unreachable from the runner. Re-run the failed job; it has succeeded on the retry. Do not "fix" anything in response to it.
- **Check the deploy after every push to `master`.** A failed deploy is silent: `master` moves ahead and production keeps serving the old container. On 2026-09-04 production was found running a commit from 2026-08-23 for exactly this reason.
- **Always merge to master after building:** once a change builds clean on its feature branch (compiles / tests pass), merge it to `master` and push so Railway deploys. Standing authorization — no need to ask each time.
