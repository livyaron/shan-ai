# Weekly master file → projects (sync, exec summary, contracts, targets)

<!-- Moved verbatim from the root CLAUDE.md on 2026-10-26. Loads only when Claude touches a matching file. -->

- **קובץ המאסטר השבועי — היסטוריה (PLAN.md P0):** `project_weekly_entries` auto-creates via `create_all` (one row per project per `פירוט שבועי <date>` column; **future** columns need `ALTER TABLE project_weekly_entries ADD COLUMN IF NOT EXISTS ...`). The five captured columns (`finish_date_text`, `controller`, `short_supervisors`, `short_testers`, `critical_tier`) on `projects` + `project_snapshots` are ALTERed in at startup (`app/main.py`). Snapshots are stamped with the **report date** (`project_sync.resolve_report_date`: filename → newest weekly column → today), never the upload day. A file older than `_report_horizon` is **replayed as history**: it adds snapshots + weekly entries, never touches live `projects` rows, returns no `identifiers` (the caller deactivates every project missing from that list — an old file would otherwise kill newer projects), and fires no briefs/reports. Weekly entries keep the newest `source_report_date` — an older file never overwrites a newer file's text. `דוח שבועי טיוטה` sheets are skipped entirely. `יעד חשמול מסתמן` prose is kept in `finish_date_text` AND read (see "שלושת היעדים" below) — a date the text calls missed is never the forecast. Historical files go in through the admin-only `POST /dashboard/projects/backfill` ("📚 טעינת היסטוריה" on the projects page): `force_history=True` for every file, oldest first. `pick_master_sheet` picks the `…עדכני` sheet when no sheet is given — never go back to "first sheet" (newer workbooks open with a one-cell macro sheet).
- **תקציר הנהלה → דשבורד פרויקטים (2026-10-16):** the master upload syncs ONLY the record sheet (`pick_master_sheet` → `דוח שבועי עדכני`). It used to sync every sheet, and the workbook's other tabs (`כל הפרויקטים כולל שושים`, `מנוע חשמולים`, `סיכוני דחייה`…) became ~550 phantom active projects (817 on the dashboard vs. the file's 263). `project_sync.deactivate_missing` (guard `MIN_INVENTORY`) is the only deactivation, and both upload paths call it. The `תקציר הנהלה <date>` sheet is parsed by `app/services/exec_summary.py` (generic: KPI pairs, titled sections, header rows; the number of KPIs/rows follows the file) and stored in `project_exec_summaries` (auto-created) after a LIVE sync only. **One number everywhere (user, 2026-10-16):** `app/services/project_kpis.py` is the ONLY definition of every projects card — the dashboard tile + view, the patterns page and the list behind every card all count the SAME rows: the pattern engine's live projects (`pattern_service.compute_cached` on the dashboard, fingerprint-busted, so it never lags the patterns page), filtered by `insight_access.view_for` ("mine") — and `insight_access.summarize`/`_PROJECT_TESTS` read `ENGINE_KPIS` from there. Population = ACTIVE projects only; finished ones are shown apart ("263 בקובץ · 41 הסתיימו") — user decision. The summary sheet's KPIs are its own Excel formulas (COUNTA/COUNTIF/COUNTIFS) — `exec_summary.resolve` re-runs each over the record sheet at upload into the identifiers it counts, and the card counts those over the active rows; a formula it cannot re-run exactly keeps the file's number, marked, with no list. A card's number is always `len(rows_for(key))` (tested). The dashboard shows CARDS ONLY — every list is behind a click: `GET /dashboard/projects/kpi/<key>[?scope=mine]` (any logged-in user, like the projects page) and the summary's tables at `GET /dashboard/projects/summary/<i>`. Numbers on the dashboard use `--num` (Heebo), never Karantina (its 6 and 8 read alike).
- **התקשרויות קבלנים ותיחורים (2026-10-17):** the master file's `סטטוס התקשרויות קבלנים ותיחורים` sheet → `GET /dashboard/projects/contracts` (any logged-in user, like the projects page; button "🤝 התקשרויות ותיחורים"). `app/services/contracts_sheet.py` is the ONLY reader: `parse_rows` is pure and maps columns BY HEADER (the name column's header is empty in the file), `analyse` makes every card/finding a count of payload rows. Stored in `project_contract_sheets` (auto-created) after a LIVE sync only, like the exec summary. The status column is a diary — the stage is the furthest step the text says already HAPPENED (`LADDER`); a plan ("צפי ל…", "נקבע ל…", a postponed "נדחתה ל…" counts at its last date, a cancelled tour never) is not a step. Past/plan is judged against the sheet's OWN date (lone date in the header, else its newest diary step); the ground-entry runway against the REPORT date — and the page says how far apart they are (the 14.10 file's sheet was last touched 09.07). Only colours the sheet's own legend names are read. **No money on this page (user, 2026-10-17):** every amount (award, package, threshold) is replaced by `REDACTED` in `_clean` as the sheet is read, and `latest()` runs `redact_payload` on every stored payload (rows saved before the rule still carry amounts) — never add an amount field, card or column back. No model reads this sheet.
- **שלושת היעדים — תכנית / מאושר / מסתמן (user decision 2026-10-16):** prose in a target cell is READ by `app/services/target_reading.py` (pure, rules only), never shown raw alone: plain date the parser missed · staged (compared by its LAST date) · "לא מאושר" (a forecast, flagged) · missed ("לא אפשרי" — that date is NEVER the forecast; a LATER date in the same text is) · energized (its date is when it WAS energized, never a forecast) · partly energized · no target (+ reason: נגה / תכנון / היתר / קבלן). Month-only/year-only = last day, `approx`. The sync stores the read date in `estimated_finish_date` (text stays in `finish_date_text`); `canonical_snaps` applies the same reading to older snapshots. `יעד חשמול מאושר ע"י מנהל האגף` → `approved_date`/`approved_text` on `projects` + `project_snapshots` (ALTERed at startup). `target_reading.compare` is the ONE definition: `over_approved` = forecast > approved + `OVER_APPROVED_DAYS` (15); an EARLIER forecast is not flagged (user decision); `approved_lost` = approved target but no forecast date. Shown on the dashboard projects view, the project page (the three side by side) and the patterns page (tiles + drill + 🟠 triage rule — the approved target is the division manager's).
